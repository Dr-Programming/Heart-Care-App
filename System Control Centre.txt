System Control Centre: Detailed Implementation Roadmap

We'll build a standalone application called System Control Centre (SCC).

It will be a separate React application with its own interface, backend monitoring layer and Docker containers. It will monitor your existing application without interfering with its normal operations.

The objective is to give judges a live view of how your system performs while Admin, Researcher and Mobile users interact with it.

I'll structure this as an implementation plan that you can follow phase by phase.

1. Final architecture

You currently have:

We'll introduce:

Important architectural decision: Prometheus collects and stores metrics. Your Monitoring API retrieves those metrics and supplies them to React.

The React application should never directly access Prometheus or PostgreSQL.

This separation also allows us to secure the monitoring infrastructure independently.

4. Implementation roadmap

Now the actual development work.

I'd divide this into eight phases.

Phase 1: Instrument the existing Spring Boot backend

Objective: Make your existing backend expose performance metrics.

You don't need to modify your business logic extensively.

Step 1. Add dependencies

In your existing backend's pom.xml:

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>

<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
Step 2. Configure Actuator

In application.properties:

management.endpoints.web.exposure.include=health,prometheus,metrics

management.endpoint.health.show-details=never

management.prometheus.metrics.export.enabled=true
Step 3. Test the endpoints

Start your backend.

Check:

http://localhost:8080/actuator/health

And:

http://localhost:8080/actuator/prometheus

The second endpoint should expose metrics in Prometheus format.

Keep these endpoints accessible only to your monitoring infrastructure, not publicly through ngrok.

Step 4. Add custom metrics

Micrometer allows you to measure application-specific behaviour.

For example:

@Component
public class ApplicationMetrics {

    private final Counter activityCounter;

    public ApplicationMetrics(MeterRegistry registry) {

        this.activityCounter = Counter.builder("app.user.activities")
                .description("Total user activities")
                .register(registry);
    }

    public void recordActivity() {
        activityCounter.increment();
    }
}

Whenever a user activity is successfully processed, increment the counter.

Important: Don't create a metric label for every user ID, record ID or URL containing dynamic parameters. That creates high-cardinality metrics and can overwhelm Prometheus.

Also, your existing activity tracking and monitoring metrics should remain separate. One stores business events; the other measures system behaviour.

Phase 1 completion criteria:

Actuator operational.
Prometheus metrics endpoint working.
Custom application metrics available.
Phase 2: Configure Prometheus

Objective: Collect and store metrics automatically.

Create a new directory:

monitoring/
│
├── prometheus/
│   └── prometheus.yml
│
├── postgres-exporter/
│
├── windows-exporter/
│
└── docker-compose.monitoring.yml

Create prometheus.yml:

global:
  scrape_interval: 5s

scrape_configs:

  - job_name: 'spring-boot'
    metrics_path: '/actuator/prometheus'
    static_configs:
      - targets:
          - 'backend:8080'

  - job_name: 'postgresql'
    static_configs:
      - targets:
          - 'postgres-exporter:9187'

We'll add Windows Exporter and container monitoring targets once those services are configured.

Important

Your Prometheus container must share a Docker network with the backend and PostgreSQL exporter.

If you're using separate Docker Compose files, explicitly create and attach them to a shared external network.

For example:

docker network create app-network

Then attach the relevant services to app-network.

Don't expose Prometheus publicly.

Test Prometheus

Open:

http://localhost:9090

Navigate to:

Status → Targets

You should see your Spring Boot target reporting UP.

Phase 2 completion criteria:

Prometheus running.
Backend metrics collected.
Targets reporting healthy status.
Phase 3: PostgreSQL monitoring

Objective: Monitor database performance independently.

First, enable pg_stat_statements.

In PostgreSQL configuration:

shared_preload_libraries = 'pg_stat_statements'

Restart PostgreSQL and execute:

CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

Create a dedicated monitoring account rather than using your application's database credentials.

For example:

CREATE USER monitoring_user
WITH PASSWORD 'your-secure-password';

Grant only the permissions required by the exporter and PostgreSQL version.

The PostgreSQL Exporter should collect:

Database connections.
Transaction statistics.
Database size.
Cache statistics.
Query statistics.
Lock information.

Official repository:

PostgreSQL Exporter GitHub

One important consideration

PostgreSQL query statistics and database-wide statistics aren't necessarily updated in real time at every instant.

Use Prometheus sampling to show trends rather than claiming every value represents an instantaneous measurement.

Phase 3 completion criteria:

PostgreSQL exporter operational.
Prometheus collecting database metrics.
Connection and transaction statistics visible.
Phase 4: Server and Docker monitoring

Objective: Monitor the machine actually running your application.

Because your server runs Windows, use Windows Exporter.

Install it on the Windows host.

It can expose metrics for:

CPU.
Memory.
Disk.
Network.
Operating system.

Configure Prometheus to scrape its metrics endpoint.

For Docker containers, start with:

docker stats

For automated monitoring, investigate cAdvisor or Docker Engine metrics.

Don't assume cAdvisor will provide complete container metrics under Docker Desktop on Windows. Validate its output in your actual environment.

Phase 4 completion criteria:

Host CPU metrics available.
Host memory metrics available.
Disk and network metrics available.
Docker container resource usage available.

5. Phase 7: Load testing and performance validation

This is probably the most valuable phase for your judging demonstration.

A dashboard showing CPU at 20% is not particularly impressive by itself.

A dashboard showing how the system behaves when 30 users interact simultaneously is much more meaningful.

Use Apache JMeter.

Official documentation: Apache JMeter

Suggested test scenarios
Test	Concurrent users	Duration
Baseline	1	2 minutes
Small load	5	5 minutes
Medium load	15	5 minutes
High load	30	10 minutes
Stress test	Increase gradually	Until bottleneck

These are proposed test levels, not claims about your application's capacity.

Simulate actual operations:

Login.
Search.
Retrieve records.
Submit forms.
Update records.
Generate reports.
Record user activities.

Include realistic think time between operations.

What judges should see

Run JMeter on another machine while displaying System Control Centre on a separate screen.

As users increase:

Requests per second should increase.
CPU utilisation may increase.
Database activity should increase.
Response times may change.
Memory consumption should be visible.

If performance remains stable, you have measurable evidence of that stability.

If performance degrades, you can identify where the bottleneck occurs.

That is considerably more useful than simply claiming that the system is scalable.

6. Phase 8: Security and deployment

Before the demonstration, lock down the monitoring infrastructure.

Your final Docker deployment could look like this:

docker-compose.yml

services:

  backend:
    # Existing backend

  postgres:
    # Existing PostgreSQL

  admin-web:
    # Existing admin

  researcher-web:
    # Existing researcher

  monitoring-api:
    # New monitoring API

  monitoring-web:
    # New React application

  prometheus:
    # Metrics collection

  postgres-exporter:
    # Database metrics

  grafana:
    # Optional internal troubleshooting

Windows Exporter runs on the Windows host rather than as a normal Linux container.

Access control

I recommend:

Application	Access
Admin	Local network
Researcher	Local network
Mobile API	Ngrok
System Control Centre	Local network only
Prometheus	Internal Docker network only
PostgreSQL	Internal Docker network only

The monitoring dashboard should require administrator authentication.

Do not expose:

Prometheus directly through ngrok.
PostgreSQL to the public internet.
Detailed Actuator endpoints publicly.
Environment variables or database credentials.
User personal information.

Also configure retention for Prometheus so monitoring data doesn't gradually consume all available disk space.

10. Before we start coding: Three architectural decisions

I want to settle three things before we begin implementation.

1. Monitoring API

I'd prefer another Spring Boot application, separate from your existing business backend.

This means monitoring failures won't directly affect the business API.

2. Dashboard authentication

Should System Control Centre use your existing Admin login/authentication system, or should it have a separate administrator login?

My recommendation is to reuse your existing authentication mechanism if it supports appropriate administrator roles, rather than maintaining another set of credentials.

3. Historical monitoring data

I'd use Prometheus for time-series metrics and retain them for approximately 15 days initially. Your PostgreSQL database should remain dedicated to application data rather than becoming a second metrics database.

Final architecture decision

This is the structure I'd aim to deliver:

Application	Purpose
Admin	Administrative operations
Researcher	Research operations
Mobile	Remote access
System Control Centre	Infrastructure and application performance monitoring
